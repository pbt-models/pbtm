# Developing pbtm

Notes for maintainers: the day-to-day workflow, and how to cut a
release, tag it on GitHub, submit it to CRAN, and publish the pkgdown
site. This file is excluded from the package build (`.Rbuildignore`).

## Setup

``` r

install.packages(c("devtools", "usethis", "roxygen2", "testthat", "pkgdown",
                   "rcmdcheck", "spelling", "urlchecker"))
devtools::install_dev_deps()   # everything in Imports and Suggests
```

To use the GitHub helpers in usethis (releases, PRs), you need a GitHub
personal access token: `usethis::create_github_token()`, then
`gitcreds::gitcreds_set()`. Check with `usethis::gh_token_help()`.

## Day to day

| Task | Command |
|----|----|
| Load the package for interactive use | `devtools::load_all()` |
| Regenerate `man/` and `NAMESPACE` from roxygen comments | `devtools::document()` |
| Run the tests | `devtools::test()` |
| Full check, as CI runs it | `devtools::check()` |
| Spell check (add real words to `inst/WORDLIST`) | `spelling::spell_check_package()` |
| Preview the website | [`pkgdown::build_site()`](https://pkgdown.r-lib.org/reference/build_site.html) (writes to `docs/`, which is git-ignored) |
| Rebuild the example datasets from `data-raw/*.csv` | `source("data-raw/datasets.R")` (needs readr) |

Never edit `man/*.Rd` or `NAMESPACE` by hand; they are generated by
roxygen2.

Work on a feature branch and open a pull request into `main`. The
**R-CMD-check** workflow runs `R CMD check` on Windows, macOS, and Linux
for every push and pull request, and the **pkgdown** workflow
test-builds the site. Merge only when both are green.

Most of the tests run everywhere, but the mixture-fitting tests and the
fresh-session namespace test call `skip_on_cran()`. They run in CI and
under `devtools::test()`/`devtools::check()` (which set
`NOT_CRAN=true`), but not on CRAN’s machines, because they are slow.

## Versions

pbtm uses [semantic versioning](https://semver.org/):
`major.minor.patch`.

- **patch** (0.3.0 → 0.3.1): bug fixes only.
- **minor** (0.3.0 → 0.4.0): new features, or breaking changes while the
  package is below 1.0.0.
- **major** (→ 1.0.0): the API is stable; from then on, breaking changes
  bump the major version.

Between releases, `main` carries a development version with a fourth
component, e.g. `0.3.0.9000`. Add a bullet to the top section of
`NEWS.md` (headed `# pbtm (development version)`) for every user-facing
change as you make it, so the release notes are already written at
release time.

`usethis::use_version()` bumps `DESCRIPTION` and `NEWS.md` together:
`use_version("patch")`, `"minor"`, `"major"`, or `"dev"`.

## Releasing

A release is: bump the version, check thoroughly, submit to CRAN, and
once CRAN accepts it, tag the release on GitHub. The GitHub release
triggers a rebuild of the website.

The easiest way to not miss a step is to run
`usethis::use_release_issue()`, which opens a GitHub issue with a
checklist tailored to this package. The steps it lists are summarized
here.

### 1. Prepare

On `main` (or a release branch merged via PR), with a clean working
tree:

``` r

usethis::use_version("minor")   # or "patch" / "major"; drops the .9000
```

Then edit `NEWS.md`: change the heading to the new version and tidy the
bullets. Also check:

- `README.md` is current (e.g. the installation instructions once on
  CRAN).
- `urlchecker::url_check()` finds no broken links (CRAN rejects them).
- `spelling::spell_check_package()` is clean.

### 2. Check

CRAN runs `R CMD check --as-cran` on several platforms, so check on
those platforms before submitting. All of these should report 0 errors
and 0 warnings; any NOTEs must be explained in `cran-comments.md`.

``` r

devtools::check(remote = TRUE, manual = TRUE)  # local, with CRAN's incoming checks
devtools::check_win_devel()                    # Windows, R-devel (results by email, ~30 min)
devtools::check_mac_release()                  # macOS (results by email)
rhub::rhub_check()                             # Linux sanitizers etc., via GitHub Actions
```

`rhub::rhub_check()` runs in this repository’s GitHub Actions; the first
time, run `rhub::rhub_setup()` and commit the workflow file it creates.

The win-builder and mac-builder results are emailed to the
**maintainer** listed in `DESCRIPTION`, not to whoever ran the command.

`R CMD check` on a first submission always gives the NOTE “New
submission”; that is expected.

### 3. Submit to CRAN

Create `cran-comments.md` (once; update it for each release) with
`usethis::use_cran_comments()`. It summarizes the check results and
explains any NOTEs. For example:

``` md
## R CMD check results

0 errors | 0 warnings | 1 note

* This is a new release.
```

Then submit:

``` r

devtools::submit_cran()
```

This builds the package, uploads it, and writes a `CRAN-SUBMISSION` file
recording the commit that was submitted. CRAN then emails the maintainer
(Pedro Bello) a link that **must be clicked to confirm the submission**.
Commit `CRAN-SUBMISSION` and `cran-comments.md`.

CRAN review takes from a day to a few weeks. First submissions are
reviewed by a person and often come back with requests (e.g. about the
Description text, examples, or writing to the user’s home directory).
Fix them, bump the patch version if needed, and resubmit, noting the
changes in `cran-comments.md`.

CRAN policy: don’t submit updates more often than about every 1-2
months.

### 4. Tag and publish the GitHub release

Once CRAN accepts the package (you’ll get an email, and it appears at
`https://cran.r-project.org/package=pbtm`), tag the release:

``` r

usethis::use_github_release()
```

This creates the `vX.Y.Z` git tag on the commit recorded in
`CRAN-SUBMISSION` (so the tag matches exactly what CRAN has), publishes
a GitHub release with the `NEWS.md` section as its notes, and deletes
`CRAN-SUBMISSION`. Publishing the release triggers the pkgdown workflow,
which rebuilds the site.

To do it by hand instead:

``` sh
git tag -a v0.3.0 -m "pbtm 0.3.0"
git push origin v0.3.0
```

then on GitHub, **Releases → Draft a new release**, choose the tag, and
paste the `NEWS.md` section as the description.

### 5. Start the next development cycle

``` r

usethis::use_dev_version(push = TRUE)   # 0.3.0 -> 0.3.0.9000, adds NEWS heading
```

### GitHub-only releases

To publish a version without submitting to CRAN (e.g. before the first
CRAN release), follow steps 1-2, merge to `main`, then run step 4
(`usethis::use_github_release()` falls back to the current `HEAD` of
`main` when there is no `CRAN-SUBMISSION` file). Users can then install
that exact version with
`remotes::install_github("pbt-models/pbtm@v0.3.0")`.

## Website (pkgdown)

The site at <https://pbt-models.github.io/pbtm/> is built by
`.github/workflows/pkgdown.yaml` on every push to `main` and every
published release, and deployed to the `gh-pages` branch. It is
configured in `_pkgdown.yml`:

- The **Reference** page groups the help topics. Every exported function
  must be listed there, so when you add one, add it to a section (or the
  site build fails).
  [`pkgdown::check_pkgdown()`](https://pkgdown.r-lib.org/reference/check_pkgdown.html)
  checks this.
- The **Get started** article is `vignettes/pbtm.Rmd`; the other
  vignettes are listed under **Models**. Add new vignettes to the
  `articles` section.
- The changelog is built from `NEWS.md`.

**One-time setup** (repository admin): after the workflow has run once
on `main` and created the `gh-pages` branch, go to **Settings → Pages**
and set *Source* to *Deploy from a branch*, branch `gh-pages`, folder
`/ (root)`. Then add the site URL to the repository’s *About* box on
GitHub.
